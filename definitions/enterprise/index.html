Infrastructure and sovereignty

Your cloud, your region, or your own hardware.

One VM running the same images in the same arrangement, whatever size you run it at. Your operations team can read the whole deployment in an afternoon.

Deployment options→
Three sizes, one shape
Sizes scale the machine and the data stores, never the shape of the system. Changing size is a variable, a re-apply and a redeploy.
AWS, DigitalOcean, Azure, or none of them
Nothing about the platform requires a cloud. The images run on a VM you already own, and you bring your own entry point: terminate TLS and forward to the engine.
Only 443 is open
SSH, Canvas and the log viewer are restricted to an address you nominate, and the builder surface binds to loopback so it is not routable at all. Firewall rules live in the cloud provider, not on the VM.
Your Terraform, your version control
Provisioning ships to you and is run by you. We do not hold a key to your estate because there is nothing for a key to open.
Governance and access

Roles and permissions, on every integration and every workflow.

A person holds roles, a role grants permissions, and the platform gates on permissions. Both ride the access token as separate claims, so your identity provider stays the source of truth.

Who can run it→
Permissions are yours to invent
A permission is always noun and verb: workflow:author, marketplace:publish, admin:access. A deployment can define finance:approve without the platform knowing it exists.
Every node declares who may run it
The block is compulsory, not optional. That is the point: a reviewer can tell the difference between a node that was considered and left open, and a node nobody thought about.
The workflow author can only tighten it
The same node legitimately faces staff on one workflow and customers on another, so the person building that workflow sets the rest. Neither side can loosen the other.
Default is deny
A definition that reaches the executor declaring nothing is treated as requiring authentication. Anonymous callers arrive with a synthetic identity carrying no roles, so they fail every role requirement naturally.
Your provider, not ours
Auth0 today, Entra or Cognito tomorrow, with no code change. The gate is default-deny and lives in the application, so no proxy is ever load bearing for security.
Integration safety

An integration is a declaration, not code we run on your behalf.

Every integration is interpreted by the platform rather than executed as arbitrary code, which is what makes the two controls below possible at all.

Security posture→
Declared hosts, deny by default
Every host an integration may call is declared in its package. HTTPS only, and checked twice: when the package is linted, and again at run time after the URL has been built. It cannot construct its way to an undeclared destination.
A content hash
The composed definition, including its host list, is hashed. The hash is checked when the definition is loaded, so a definition that changed after it was accepted does not quietly run.
Publishing arrives as pending
Whoever runs the universe sees the hosts it wants to call, the credentials it needs and the access it demands, and accepts it before it can run. An integration that later reaches for something new pauses again.
Credentials and secrets

A key is decrypted at the moment it is used, and handed to one integration.

Nothing an author writes ever contains a value. The manifest names the credential; the value is entered once and lives only in your database.

Credentials→
Encrypted per field, at rest
Only fields marked secret are encrypted, and they are decrypted at the moment an integration runs.
No shared blast radius
An integration receives only the credentials it declared. Two integrations in one workflow cannot read each other's keys, whatever either of them writes, because credentials are addressed by name rather than discovered.
Every deployment generates its own
Database and Redis passwords are random per universe, and so is the credential encryption key. None is shared between deployments and none is known to us.
Observability and audit

Reconstructed after the fact, not inferred.

Agent activity is recorded including the content that produced each decision, so an answer a customer received can be explained rather than guessed at.

Security posture→
Node by node
Every run and every step, with the real inputs and outputs, kept in your own database.
Into the stack you already run
Small deployments ship a log viewer restricted to your operator address. Larger ones turn it off and point the container logging driver at Splunk, ELK or Datadog.
Token accounting per run
Usage is recorded per run and per step, so spend is attributable to a workflow rather than arriving as one monthly number.
Models

Bring your own models, on your own provider contract.

Bedrock, OpenAI, or a model running in your own account and your own region. Swapping one is configuration, not a rebuild.

Your keys, your contract, your region
The provider relationship is yours. We are not in the path of it and we do not resell it.
Guardrails applied, not reinvented
Where your provider has a policy engine, the platform applies your policy rather than substituting one of its own. Your guardrail configuration stays the thing that governs.

Enterprise
Still open

Two items are gaps rather than controls.

Both are known, both are tracked, and neither is discovered by a reviewer first.

The credential encryption key has a fallback default in code
A universe provisioned by the Terraform is given a generated key, so a correctly provisioned deployment does not use the default. The fallback should not exist, and removing it is required before any internet-facing deployment.
One connection carries its token in the query string
That is why load balancer access logs are switched off in the entry point requirements. Moving the token to a header lifts both the gap and the restriction.
